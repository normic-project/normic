# Phase 4 escrow threat review

Internal design review, not an external audit. Assets: user root ownership, bounded session authority, USDG escrow obligations, authentic job results, immutable journals and private credentials/payloads.

| Threat                               | Implemented control                                                                                              | Remaining trust / launch work                                                                                                 |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Session compromise / wallet takeover | Owner root never enters Normic; selector-only sessions; escrow onchain caps and expiry                           | Secure custodian and owner grant provisioning are not connected; external review required                                     |
| Unauthorized spend / IDOR            | Scope + ownership + current credential checks, separate owner JWT, private buyer/provider membership             | Runtime database credentials must be isolated from clients                                                                    |
| Approval abuse                       | No agent approval selector; human exact/minimal approval calls                                                   | Owner must inspect wallet prompts; existing allowances may outlive local revocation                                           |
| Malicious calldata                   | Server constructs one escrow call, zero ETH, selector/destination validation, simulation                         | Custodian must decode complete AA calldata and recompute signing hash, not trust provider payload blindly                     |
| Reentrancy / theft                   | Guarded funding and settlement, CEI, SafeERC20, no admin sweep                                                   | Canonical token and account implementation remain trusted dependencies                                                        |
| Double settlement / replay           | Terminal contract states, chain/contract/terms-derived ID, unique events/journals/operations                     | An uncertain submission requires reconciliation, never a retry loop                                                           |
| Wrong-chain signing / RPC spoofing   | Chain checks before simulation/sign/send, canonical USDG address, pinned escrow bytecode, finalized block hashes | A malicious sole RPC can lie; use independent providers and monitoring before launch                                          |
| Decimal / amount error               | Decimal strings → BigInt, precision/uint256 bounds, onchain decimals, explicit cap                               | Token upgrades must be monitored; no floating-point money                                                                     |
| Price races / concurrent funding     | Locked immutable agreement and price snapshot, row locks and unique constraints                                  | Unfunded reservations have timeouts; monitor abuse and stale plans                                                            |
| Fake logs / fake revenue             | No public event-ingestion endpoint; verified finalized receipt decoder; immutable provenance                     | Indexing-role compromise is outside ordinary client trust boundary                                                            |
| Result privacy                       | Private payloads and random-salted onchain result commitment                                                     | Database access and backup encryption remain operator responsibilities                                                        |
| Front-end tampering                  | No server root key; chain/account checks, explicit wallet prompts, simulation                                    | A compromised UI can deceive a root wallet user; CSP, supply-chain review and trusted transaction display remain launch gates |
| Admin compromise                     | Explicit admin/resolver, delayed admin transfer, no sweep/upgrade                                                | Resolver can choose the winner of a dispute; multisig and governance controls required                                        |
| Direct transfer leaderboard abuse    | Capital/unattributed observations separate; only escrow releases create revenue                                  | Same-owner self-payments blocked, but Sybil resistance and wash trading are not solved                                        |
| Finality / outage / reorg            | Finalized-only accounting, checkpoint hash validation, atomic reconciliation                                     | Catastrophic finalized reorg needs manual response; no automatic history rewriting                                            |
| Gas abuse                            | No sponsorship policy enabled; no arbitrary ETH calls                                                            | Configure a restrictive sponsor policy only after independent review                                                          |

Policy loss or provider outage fails closed for new actions. Offchain local revocation is not claimed to be onchain revocation. Previously signed/in-flight actions remain possible. Unsolicited escrow donations cannot be prevented or converted into verified revenue.

Phase 5 trading threats and controls are reviewed separately in [TRADING_THREAT_MODEL.md](TRADING_THREAT_MODEL.md).
